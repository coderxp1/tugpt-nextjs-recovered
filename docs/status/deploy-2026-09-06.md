### Both numbers on that line are counted, not stated

Checked against the implementation, not the documentation:

| Part of the line | Where it comes from |
|---|---|
| `55 migration(s) in this checkout` | `repoVersions.length`, from `readdirSync` of `supabase/migrations` (`schema-expectations.ts:126`, `milestone1.ts:197`) |
| `database has 55` | `ledger.versions.length`, rows returned by `applied_migration_versions()` |
| `latest 20260905000001` | last element of the ascending ledger versions — derived from the database, not from a filename in the repo |

No total is written down anywhere in that path, so the line cannot be stale in
the way the previous sheet's prediction was. `docs/server-migrations.md` §4
repeats the same sample, and `apps/worker/tests/server-migrations-doc.test.ts`
computes the expected number with `readRepoMigrationVersions()` — the same
function the preflight uses. If the doc and the checkout ever disagree, that
test fails in CI rather than an operator discovering it on a server.

## 4. Rebuild and start the new service

`transcription-worker` is a **new compose service** (added by this PR) and it
shares the `tugpt-worker:latest` image with the ingest and draft workers, so it
needs the image rebuilt, not just `up`:

```bash
docker compose -p tugpt build transcription-worker
docker compose -p tugpt up -d
sh deploy/check-host.sh          # "0 failed, 0 warned, 0 skipped"
docker compose -p tugpt ps       # 5 services, all healthy: web, caddy,
                                 # whatsapp-worker, draft-worker, transcription-worker
```

(No database container — Supabase is hosted, which is also why §2's baseline
check has to go to `psql` rather than to `docker exec`.)

It is safe to boot with no credentials configured: it reads no provider key at
startup — those come from `platform_secrets` when a job is actually claimed —
and the queue is empty, so it polls and finds nothing.

### Deploy-timing note

Its `stop_grace_period` is **330s**, not the draft worker's 90s: an attempt can
legitimately wait 300s on Gladia plus a media download, and SIGTERM does not
cancel an in-flight attempt. A `restart`/`up -d` issued while a transcription
is running will therefore look like it is hanging for up to five and a half
minutes before the container is replaced. With `voice_transcription` off there
is no such attempt, so this deploy is not affected; it is §5's deploy that can
be. Do not reach for `docker kill` to shorten it — the grace period exists so
the worker stops *between* jobs rather than mid-attempt.

## 5. To actually enable transcription later

Three steps, in this order, none of them part of this deploy:

1. **Install the Gladia key** — `docs/credential-handover.md` §2:
   `node dist/secrets-cli.js put --provider gladia --secret-name api_key`.
   `TUGPT_SECRET_KEY_PLATFORM_V1` is already on the server (09-04).
2. **Install a Meta Graph access token**, same way. **This credential does not
   exist yet.** `WHATSAPP_APP_SECRET` / `WHATSAPP_VERIFY_TOKEN` are
   inbound-webhook only and cannot fetch media. Until step 2 is done, voice
   notes dead-letter with `TRANSCRIPTION_MEDIA_AUTH_ERROR` — the agreed interim
   state, and the correct one: failing before any bytes move means nothing
   reached Gladia and nothing was billed.
3. **Enable `voice_transcription` for one organization.** The enqueue reads
   *both* `voice_transcription` and `ai_draft_generation`, so an organization
   with drafts off is never transcribed at all.

Per `docs/credential-handover.md`: the value is typed at the prompt with echo
off and read twice; it is never an argument, so it does not reach shell
history, `argv`, or `/proc/*/cmdline`.

## 6. What to watch once it is enabled

`docs/controlled-rollout.md` has the full outcome table. The two that are
specific to this change:

- **`TRANSCRIPTION_TIMEOUT` names work that is already paid for.** We stopped
  waiting after 300s; Gladia is still running the job. The handle to collect it
  is `transcription_jobs.provider_job_reference`, which is why that column is
  written *before* any polling and why a redelivered job resumes rather than
  resubmits.
- **A voice note transcribed twice is the one failure that costs money per
  occurrence.** Stop the worker and check that `record_transcription_submission`
  was being written. It refuses to overwrite a different reference (`P3I08`),
  so if it ever happens, the refusal is the evidence and it is a bug, not drift.
